# 发布流程

从"能跑"到"发出去"，中间有一串不能省的检查。少一项就别发。

## 一、发布前检查清单

### 构建可复现
- [ ] 干净环境下按 [REPRODUCE](../REPRODUCE.md) 从原盘重建
- [ ] 重建产物与原产物 SHA-256 完全一致
- [ ] 构建过程未修改任何输入文件

### 内容验收
- [ ] 剧情、菜单、战斗、整备、简报、辞典、结算逐屏过一遍
- [ ] 每屏留存验收记录（屏幕名 + 结果 + 截图路径）
- [ ] 无空白字、无问号、无旧译文残留
- [ ] 字形基线一致，无"忽上忽下"
- [ ] 无新增黑屏、卡死、花屏

### 结构审计
- [ ] 差异只落在允许区域（图集像素、目标记录字段、文本条目）
- [ ] slot 数 / 码表 / FontMap 结构未变
- [ ] 未改动与本次内容无关的资源

### 文档齐备
- [ ] `CHANGELOG.md` 已写本版本条目
- [ ] `docs/00-项目状态.md` 已更新到本版本
- [ ] Release 说明写明**未验证范围**
- [ ] 原盘校验值、产物校验值已记录到 `manifests/`

### 合规
- [ ] 仓库内无 ISO、无字体原文件、无游戏素材
- [ ] Release 资产只有补丁与校验清单
- [ ] 许可与作者声明已按最终署名替换

## 二、产物

| 文件 | 说明 |
|---|---|
| `ace3-zh-<版本>.xdelta` | 对日版原盘的差分补丁 |
| `SHA256SUMS.txt` | 补丁自身与成品镜像的校验值 |
| `安装说明.txt` | 三步走：核对原盘 → 打补丁 → 校验成品 |
| `manifests/<版本>.json` | 构建输入输出全量校验记录 |

**不放进 Release 的东西**：ISO、字体文件、测试用存档、日志、截图压缩包（截图放仓库 `docs/`）。

## 三、Release 说明模板

```markdown
## 本版本

<一句话说清修了什么>

## 已知问题

- <明确列出没修的问题，不要写"应该不影响">

## 未验证范围

- <列出没跑过的平台/流程>

## 安装

1. 确认原盘 SHA-256 为 <值>
2. `xdelta3 -d -s original.iso ace3-zh-<版本>.xdelta ace3-zh-<版本>.iso`
3. 核对成品 SHA-256 为 <值>

## 从旧版本升级

<是否需要先恢复原盘；是否需要备份存档>
```

## 四、发布后

1. 更新 `README.md` 顶部的状态（"开发中" → 当前版本号）。
2. 更新 `docs/00-项目状态.md`。
3. 在主工程写一份存档，记录本次发布对应的基线、产物哈希与验收范围。
4. 观察 Issue；**发现严重问题立即在 Release 顶部加警示**，不要等下一版默默修。

## 五、撤回

发现严重问题（大量黑屏、存档损坏、误改无关资源）时：

1. 先把 Release 标记为 Pre-release 或直接删除资产。
2. 在仓库 README 顶部加警示，说明影响范围与临时处置方式。
3. 保留 `manifests/` 记录，不要删——它是复盘依据。
4. 修复后发修订版，**不要覆盖旧版本的资产**，保留版本历史。

## 六、版本号怎么定

| 情况 | 版本 |
|---|---|
| 首次对外可用 | `1.0.0` |
| 增加或修订译文、字形 | `1.x.0` |
| 只修 bug、只改文档 | `1.x.y` |
| 破坏性变化（存档不兼容、必须重下） | `2.0.0` |

`0.x` 阶段视为开发预览，可以随时改结构，但要对外说明"不作长期兼容承诺"。
