# ACE3 统一文本检索器（第二版：第一阶段 + 第二阶段）

只读工具。输入截图上的文字 → 直接给出 EID / key / slot、原始码位、原始字节、前后文，
以及原版日文对照、权威译文对照、15 包字库覆盖和六型故障诊断。

**它不改任何东西。** 不写 ISO、不写字体包、不写权威译文表、不写工程事实库.sqlite。

第一阶段（检索）与第二阶段（诊断）都在本目录，索引 schema_version=2。
第二阶段详细报告与最终验收结果（`第二阶段交付报告.md`、`最终验收报告.md`）随汉化工程内部
工作树保存，未纳入本仓库。

> **发布版说明**：本仓库只收录检索器的三个核心模块 `locator_core.py`（解析层）、
> `build_index.py`（建索引）、`query.py`（查询与偏移反查），供二次开发与格式研究参考。
> 下文提到的 `ace3_text_find.py`、`diagnose.py`、`diag2.py`、`build_extra.py`、
> `coverage.py`、`crossver.py`、`reconcile.py`、`selftest*.py`、`bench.py`、`verify_align.py`
> 以及 `db/` 索引缓存均不在发布版内；对应的命令行子命令、第二阶段六型诊断与
> 各项验收数据来自汉化工程内部工作树，本文保留原始记录仅供对照。
> 三个核心模块需要 `tools\` 下的 `ace3_pack`、`_r104_glyphfix2`、`_r211_cmap`、
> `_r223_apply_plan` 等同级模块，发布版把它们与本目录一起放在 `tools\` 内。

## 一分钟上手：看到错字怎么办

**在工程根目录（放着 `ace3find.cmd` 的那一层）打开命令窗口，输入：**

### 用 CMD（Windows 命令提示符）

```bat
cd /d "<工程根目录>"
ace3find.cmd find 何？
```

### 用 PowerShell

PowerShell 里必须写 `.\` 前缀，否则会报「无法将 `ace3find.cmd` 项识别为 cmdlet」：

```powershell
cd "<工程根目录>"
.\ace3find.cmd find 何？
```

或者用 `cmd /c` 包一层，就不需要 `.\`：

```powershell
cmd /c "ace3find.cmd find 何？"
```

把 `何？` 换成你在游戏画面上看到的任意一段文字即可（单字、双字、半句、整句都行）。

输出直接给出：`EID / key / slot`、盘面文本、原始码位、原始字节、ISO 偏移、
原版日文、权威译文、前后文，以及一行**可复制的定位串**。

想进一步问"这条到底是错译、错码位还是缺字"：

**CMD**

```bat
ace3find.cmd diagnose --eid 4004643 --key=0,0 --slot 9
```

**PowerShell**

```powershell
.\ace3find.cmd diagnose --eid 4004643 --key=0,0 --slot 9
```

其它常用形态（CMD 与 PowerShell 只差前面的 `.\`，下面按 CMD 写）：

```
ace3find.cmd find "什么？" --context 2          # 多给两句上下文
ace3find.cmd find 月神 --iso r1354_grayline_clamp_test   # 查另一张盘
```

`ace3find.cmd` 会自动挑一个带 numpy 的 Python，不用先 `cd tools\ace3_text_locator`，
也不用记解释器路径。**负数 key 要写等号**：`--key=-1,17`。

不想用启动器时，等价写法：


## 偏移口径（`offset` 命令的依据）

一条槽在 ISO 里的真实字节区间是：

```
file_off = abs_off + base + offs[slot]
file_end = abs_off + base + (offs[slot+1] 或块尾)
```

`abs_off` 是 `locate()` 返回的块绝对偏移，**已经含 `ISOBASE`(0x422800)**，
所以上式的值就是可以直接 `f.seek()` 的 ISO 文件偏移。

这条口径不是推理，是实测过的：`eid=4004643 (0,0) slot0` → `file_off=0x3ED439F8`，
`seek` 过去读出来正好是 `<operator(21010,1)><speed(2)><color(4)>优莱卡是科拉利安……`；
`base` 非零的情况（`eid=6200 (-1,0)` `base=368`）同样对得上。
`selftest.py` 每张盘抽 5 个干净槽做「库里反查回同一 sid + ISO 回读字节相同」双重自证。

`offset` 未命中时会说明该偏移是资源头/压缩块体/未扫描 eid，并列出前后最近的槽——不装作找不到。

### 跨版本对应槽：认逻辑槽身份，不认固定物理地址

`file_off` 只是「这张盘上这个槽的字节在哪」，**不是槽的身份**。改字会让后面的偏移整体挪动。
实测例子（`eid=4004643 (0,0)`）：

| 盘 | 该块 `offs[9]` | slot9 `file_off` | slot9 文本 |
|---|---|---|---|
| R1354 | 1204 | `0x3ED43CF4` | 何？ |
| R1356 | **1202** | **`0x3ED43CF2`** | 什么？ |

正文短了 2 字节，偏移表第 9 项就从 1204 改成 1202。所以跨盘对比**不能**「按某盘的 file_off 去另一盘读」。

`diff` 用的是**逻辑槽身份 `(eid, tag, k, slot)`**：分别在 A 盘、B 盘按这个身份查各自的槽，
各自读本盘的真实字节再比。偏移表怎么变都不影响，也不会跑来比对 `(1,0)` 块的某槽。

同理，「压缩条目的 `file_off` 指向压缩块位置」这条限制也是逐盘的性质，不能跨盘套用。

### 槽号的三种口径（对旧施工记录时必须换算）

同一块文本里有三套编号，混用就会「看起来对不上」：

| 口径 | 含义 | 谁在用 |
|---|---|---|
| **偏移表原始下标** `raw_idx` | 在 `cnt` 长度的 u32 偏移表里的数组下标，含所有零项 | 旧施工记录（`idx19` / `idx30`）、zongbiao.tsv 的 `slot` 列 |
| **非零槽序号** `slot` | 把零偏移项去掉、排序后从 0 开始重编号 | **本工具全部输出**（`slot=`、`--slot`） |
| **文件偏移** `file_off` | 该槽字节在 ISO 里的真实位置 | `offset` 命令、跨盘对比时读字节 |

换算关系：`raw_idx = 该块偏移表里第 slot 个非零项的下标`。工具不输出 `raw_idx`，
但 `locate` 的输出来自同一份偏移表，可用 `reconcile.py` 的 `classify_block` 复算。

**实测两个建档过的槽，确认旧记录与本工具指的是同一个槽：**

| 槽 | 偏移表非零项 | 旧记录写法 | 本工具写法 | 是否同一槽 |
|---|---|---|---|---|
| `4004583 (0,0)`「５ｔｈ月神…」 | raw_idx `19..33` 共 15 项 | `idx=30` | `slot=11` | **是**（`raw_idx[11] = 30`） |
| `4004122/4004162 (1,0)`「又一次任由…上升了。」 | raw_idx `0,19,20,21` | `idx=19` | `slot=1` | **是**（`raw_idx[1] = 19`） |

注意 `4004122` 那块的 `raw_idx=0` 是另一条「巴尔德纳充能」（`slot=0`），
旧施工记录的 `idx=19` 修的是 `slot=1` 那条长句。搜索「巴尔德纳充能」**两条都会命中**，
不是工具给错槽——按 `slot` 区分即可。

## 怎么解码的（这决定结果对不对）

盘面**不用 CP932 解释**。

1. `_r211_cmap.code2char()` 是工程权威码表（2193 个码位），由
   `load_cur()`（tmp_r206_memfix）+ `newcode_map{r205}` + `REPAINTED`（_r211_override）合成。
2. 每条槽按 SSE 规则切：`<...>` 控制标签切走、`0x81-0x9F/0xE0-0xFC` 取双字节查表。
3. **查不到就是查不到**，输出 `〔XXXX〕` 并计入"未知码位"，绝不拿 CP932 顶替。
4. CP932 解只作为 `cp932_reference` 一列出现在 JSON 里，供对照用。

典型验证：`0x89A8 → 何`、`0x897C → 什`、`0x8957 → 么`、`0x90D1 → 赞`。

## 索引里有什么

| 表 | 作用 |
|---|---|
| `slots` | 槽级主表：eid/tag/k/slot、绝对偏移、**文件偏移区间**、原始字节、码位串、纯文本、质量分级 |
| `n2` | 单字 + 双字倒排（delta + varint 压缩），**这是"1~2 字也能秒查"的关键** |
| `codes` | 码位倒排（`code 0x89A8`） |
| `slots_fts` | FTS5 trigram，只作长句辅助，不进主路径 |
| `meta` | ISO 路径/大小/MD5、码表来源、各项计数、真实耗时、偏移口径说明 |

`meta.schema_version` 当前为 **2**（v2 增加 `file_off`/`file_end`）。库版本与代码不符时
`open_db()` 直接拒绝并提示重建，不静默复用旧结构。

**为什么不用 FTS5 trigram 做主路径**：实测 SQLite FTS5 的 trigram 分词器对 1~2 字的
查询直接返回空（`MATCH '兰顿'` → 0 行，`MATCH '兰顿在'` → 有行）。方案第三节已点明
这个坑，所以单字/双字走自建倒排。

### 质量分级 `q`

| q | 含义 | 处理 |
|---|---|---|
| 1 | 干净文本（无未知码位、无控制字节） | 正常检索 |
| 2 | 含少量未知/控制码位 | 正常检索，**诊断时优先看**（疑似缺字） |
| 0 | 未知+控制占比 >25% | 判定为数据段，不进倒排，但**记录保留** |

`q` 只是分类，不删数据。原始字节全在 `slots.seg` 里。

## 索引与盘的绑定

`meta.iso_md5` 记的是建索引时那张盘的 MD5。换盘要重建（`index --iso`），
不会静默复用旧盘结果。`find --verify` 会把命中的槽**从 ISO 重新读一遍**，
字节不一致直接标"回读不一致"。

## 第一阶段能诊断什么、不能诊断什么

能（索引内自证）：

- 该槽的原始字节、码位、在哪个 eid/块/槽、在 ISO 里的字节区间
- 码位在工程码表里有没有映射（→ 类型 C 的线索，CONFIRMED）
- 该段是不是根本不是文本（→ 数据段）
- 同槽前后文
- 跨两张盘同一槽的字节差异（→ 是否已修订）

第二阶段（`build_extra.py all` 之后）**新增能**：

- 原版日文原文对照（100% 槽对齐，T1 级）
- 权威译文对照与差异分级（SAME / SUBTEXT / DIFF / NO_SOURCE）
- 15 包静态字形覆盖（全包缺 / 部分包缺 / 全有）
- 六型诊断 A/B/C/D/E/F，每条带证据等级

**不能**——这些永远输出 UNKNOWN 或 SUSPECTED，不猜：

- 语义正确性（不能只靠字节相等自动证明）
- 某槽实机由**哪个**字体包渲染（静态覆盖 ≠ 运行时归属）
- 字形身份是否正确（E 型，需字形身份证据；OCR / 跨包投票不能作判据）
- 实机为什么显示异常（要 GS/EE 证据 → `RENDER_SUSPECTED`）

### F 型（渲染问题）的触发前提

**F 型的前提是「你在实机上确实看到了这个槽显示异常」，这是外部事实，工具推不出来。**

- 不加 `--user-report`：静态检查全部干净时，F 给 **NO_ISSUE**，主诊断写「未发现可指认的问题」。
  **「静态没查出毛病」不等于「渲染有问题」**——绝大多数槽本来就该一切正常。
- 加了 `--user-report`（你确认实机画面异常）：若文本/编码/字库/译文都排查干净，
  才把 F 立为 `RENDER_SUSPECTED` 并作为首要嫌疑。
- 若已查出 C/D/B/A 中的坏项，F 一律 `NOT_APPLICABLE` —— 先排除文本层面的原因。

诊断输出固定四段：`已确认事实 / 最可能原因 / 未验证因素 / 下一步唯一必要检查`。

## 第二阶段：三张增量表

`build_extra.py` 只**追加新表**，主表 `slots` / `n2` / `codes` / `slots_fts` 一字未改，
所以第二阶段上线不破坏第一阶段任何检索结果。

| 表 | 内容 | 建表来源 | 实测耗时 |
|---|---|---|---|
| `jp` / `jp_only` | 原版日文原文与逐槽对齐 | 原版盘（首建 220.5s，之后读共享缓存 0.8s） | 0.8s |
| `trans` / `trans_only` | 权威译文关联（rank 严格取自译文权威链） | 7 个 rank1/2 TSV，不读 ISO | 49.6s |
| `pkg_cov` | 15 包 码位→record→rect→ink 覆盖 | 15 个字体包，约 25MB | 0.7–1.4s |

**四盘实测（r979 / r1322 / r1354 / r1356）全部齐备且数字一致。**

### 日文对齐：94863 / 94863 MATCHED（100%）

原版盘与汉化盘 TOC 的 eid 集合完全相同（10343 = 10343，双向差集 0），每个 `(tag,k)` 块槽数一致。
`jp_only` 10 条是**中文盘删掉的日文残留块**（说话人名、数据段），不是对齐失败。

### 权威译文：21524 槽有源（22.69%）

```
SAME 17159 / SUBTEXT 1216 / DIFF 3149 / TEXT_ONLY 0 / NO_SOURCE 73339
匹配方式：JP_TEXT 18911 / TEXT 1786 / POSITION 827
```

四种状态必须分开理解，**不能简化成"有问题/没问题"**：

- `SAME`：一致。
- `SUBTEXT`：一方是另一方的真子串。多为 UI 短串（「确定：○」落在更长的槽里），只覆盖一部分，不能判一致也不能判不同。
- `DIFF`：都完整但不同 —— **差异候选**，不是"盘面写错"的证明（可能是后续修订未落盘）。
- `NO_SOURCE`：任何权威 rank1/2 文件里都没这条。

### 15 包字库：可判字形码位 1957 个

```
15 包全部有墨   628 (32.09%)
部分包缺        1264   其中只缺 1200002/1200003 两张 512 小图集 467 个（设计如此）
                       只有 1~2 个包有墨（更可疑）115 个
15 包全无字形     65   ← 真·缺字嫌疑（多为日文假名残留：ー は け も じ こ と あ え …）
```

另有 1557 个"码位"不在工程码表，**全部只出现在 q=2 可疑槽**，q=1 干净槽里一个都没有，

## 已知局限

1. **字体包被跳过主扫描**。15 个字体包 eid（1200000…4002057）是图集二进制，不是文本块；
   主扫描跳过它们（否则造出几千万个垃圾槽），第二阶段用 `pkg_cov` 单独读它们。
2. **VER 块枚举的边界**。`locate()` 按 `VER = 00 00 01 00` 特征找块，被它漏掉的
   非标准文本段（`ACE3_FALLBACK_BLOCKS=1` 才补的兜底块）不在这版索引里。
3. **日文原盘不单独建索引**。第二阶段是把原版盘的内容对齐进各中文盘索引的 `jp` 表，
   共享缓存只在 `db/_shared/jp_cache.sqlite`；不需要为原版盘单独建一份检索索引。
4. **多张盘 = 多份索引**。`db/<ISO名>/`，别混用；`schema_version` 不符会自动拒绝。
5. **压缩条目的 `file_off`** 指向压缩块在 ISO 里的位置，不是解压后文本的偏移——
   压缩条目本来就没有独立的文件偏移。`comp=1` 的槽共 8845 条，占 9.3%。
6. **静态覆盖 ≠ 运行时归属**。`pkg_cov` 只证明"某包里有这个码位的有效字形"，
   不能证明某槽实机由哪个包渲染。这一条在任何输出里都保持 UNKNOWN。
7. **DIFF 不等于写错**。权威译文与盘面不同只说明"有差异"，成因（未落盘 / 被覆盖 / 真错）
   需要额外证据，工具只给 SUSPECTED。

## 口径对照：旧报告 106601 槽 vs 本索引 94863 槽

**两个数字都对，口径不同，不可直接比较。** `reconcile.py` 做过完整分解（r1356 实测 181.57s）：

```
94863 = 106598（旧去重后） − 14114（旧口径把字体包内块算进来了） + 2376（旧口径三道闸门丢弃） + 3（旧口径重复 offset 多算）
```

- 旧数字来源：`tmp_ace3_15pack\r1324_regress.py:31-65` 的 `overruns()`，且 5309/106601 是**硬编码**进
  `v1361_report.py:125-126` 的，不是报告时现算。
- 旧口径**只跳了 tag 2000/2500/2001/2501，没跳 15 个字体包 eid**，把字体包内 164 块 / 14114 槽当文本槽数了进去。
- 旧口径还有三道闸门丢弃 417 块 / 2376 槽：offset 唯一率 <98%（172 块 / 1827 槽）、
  空文本（160 块 / 268 槽）、合法率 <90%（87 块 / 283 槽）。
- 新口径 = 非字体包块的全部槽，不筛闸门、按 offset 去重。

明细：`reconcile_r1356.json`
